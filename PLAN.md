# UPA (Universal Parser Automatization) — план разработки

Исходное ТЗ: `README.MD` (5 строк). Ниже — развёрнутая интерпретация, разбитая на этапы,
плюс блок предложений по развитию идеи.

**Принятые вводные (согласованы с заказчиком):**

| Решение | Выбор |
|---|---|
| Стек | Python + Playwright + FastAPI + React |
| Фокус MVP | Сбор данных (парсинг). Автоматизация ввода — Этап 7 |
| ИИ | Локальная модель через Ollama, опциональный облачный фолбэк |

---

## 1. Что именно строим (уточнённая формулировка ТЗ)

UPA — локальное настольное веб-приложение, которое превращает **любой сайт** в
**воспроизводимый конвейер данных** за счёт четырёх шагов:

1. **Изучение** — открывает URL в реальном браузере (Playwright), снимает DOM-снапшот,
   сетевые запросы, скриншоты, структуру интерактивных элементов.
2. **Понимание** — ИИ размечает элементы: «это поле поиска», «это карточка товара»,
   «это кнопка пагинации», «это цена». Результат — **карта элементов** с человекочитаемым
   описанием и стабильным селектором.
3. **Сценарий** — пользователь подтверждает/переопределяет поля, задаёт что собираем
   (одна запись / список / список с пагинацией), и это сохраняется как переиспользуемый
   артефакт — **Scenario**.
4. **Исполнение** — сценарий выполняется движком: сбор данных → нормализация →
   валидация → экспорт (CSV/XLSX/JSON/Google Sheets). Альтернативный выход — **ТЗ в
   Markdown** для внешнего ИИ-агента, если нужна нестандартная логика.

Ключевая ценность не в «спарсить один раз», а в том, что **сценарий живёт**: он
перезапускается по расписанию, чинится сам при изменении вёрстки и сообщает, когда данные
изменились.

## 2. Целевая архитектура

```
┌──────────────────────────────────────────────────────────────┐
│ Frontend (React + Vite + TypeScript)                         │
│  • Мастер «Новый сценарий»   • Визуальный выбор элементов     │
│  • Просмотр карты элементов  • Таблица результатов + экспорт  │
│  • Редактор сценариев        • Мониторинг и история запусков  │
└───────────────────────────┬──────────────────────────────────┘
                            │ REST + WebSocket (прогресс в реальном времени)
┌───────────────────────────▼──────────────────────────────────┐
│ Backend (FastAPI)                                            │
│  ┌─────────────┐ ┌──────────────┐ ┌───────────────┐          │
│  │ Crawler     │ │ Analyzer     │ │ Scenario      │          │
│  │ Service     │ │ Service (LLM)│ │ Engine        │          │
│  │ (Playwright)│ │              │ │ (extract+run) │          │
│  └─────────────┘ └──────────────┘ └───────────────┘          │
│  ┌─────────────┐ ┌──────────────┐ ┌───────────────┐          │
│  │ LLM Gateway │ │ Storage      │ │ Scheduler /   │          │
│  │ Ollama+Cloud│ │ SQLite+Files │ │ Exporters     │          │
│  └─────────────┘ └──────────────┘ └───────────────┘          │
└──────────────────────────────────────────────────────────────┘
```

**Технологии по слоям:**

- **Browser**: Playwright (Chromium), `storage_state` для авторизации, перехват
  `page.on("response")` для XHR/JSON-эндпоинтов.
- **Backend**: FastAPI + Uvicorn, Pydantic v2 для схем данных, SQLModel/SQLAlchemy + SQLite,
  APScheduler для расписаний, WebSocket для прогресса.
- **LLM**: Ollama (Qwen2.5 / Llama 3.1) через `httpx`, слой абстракции для облачного
  фолбэка. Обязательно структурный вывод (JSON Schema / constrained decoding).
- **Extraction**: приоритет 1 — прямые HTTP/JSON-запросы (быстро и дёшево), приоритет 2 —
  DOM через Playwright, приоритет 3 — LLM-извлечение по «очищенному» HTML как fallback.
- **Frontend**: React + TypeScript + Vite, TanStack Query, TanStack Table,
  overlay-разметка элементов поверх iframe/скриншота.
- **Экспорт**: pandas + openpyxl для XLSX, встроенный `csv`, Jinja2 для генерации MD-ТЗ.

**Структура репозитория (предложение):**

```
upa/
├─ backend/
│  ├─ app/
│  │  ├─ api/            # routers: sites, scenarios, runs, exports
│  │  ├─ core/           # config, logging, security, events
│  │  ├─ crawler/        # playwright driver, network capture, snapshot
│  │  ├─ analyzer/       # dom trimmer, prompts, llm gateway, element map
│  │  ├─ engine/         # selector resolver, extractors, pagination, pipelines
│  │  ├─ storage/        # models, repositories, artifact store
│  │  └─ exporters/      # csv, xlsx, json, markdown-spec
│  ├─ prompts/           # версионируемые промпты
│  └─ tests/
├─ frontend/
├─ data/                 # sqlite, snapshots, exports (git-ignored)
└─ docker-compose.yml    # опционально: ollama + app
```

## 3. Этапы разработки

Формат: **цель → содержание → критерий готовности (DoD)**. Оценки — в человеко-днях
одного разработчика, без учёта простоев на ожидании моделей.

---

### Этап 0. Каркас и инфраструктура (3–5 дней)

**Цель:** запускаемый скелет, в который дальше вставляются модули.

- Инициализация репозитория: `backend/`, `frontend/`, `data/`, линтеры (ruff, black,
  eslint, prettier), pre-commit.
- FastAPI-приложение, health-check, OpenAPI, CORS, конфиг через `.env` (pydantic-settings).
- React-приложение, сборка, прокси на API, базовый layout и роутинг.
- SQLite + миграции (Alembic), модели-заглушки.
- Один скрипт запуска (`make dev` / `run.ps1`): поднимает API, фронт, проверяет Ollama.
- Логирование (structlog), единый формат ошибок API.

**DoD:** `run.ps1` поднимает приложение, в браузере открывается UI, `/health`
возвращает 200, тест-запуск CI проходит.

---

### Этап 1. Движок браузера и снятие снапшота (5–8 дней)

**Цель:** по URL получить полный, воспроизводимый «слепок» страницы.

- Обёртка над Playwright: запуск Chromium headless/headed, эмуляция устройства,
  таймауты, обработка диалогов и cookie-баннеров (автозакрытие типовых CMP).
- **Снапшот** как артефакт, состоящий из:
  - финальный DOM (после сети и JS) + `outerHTML`;
  - скриншот полной страницы и viewport;
  - список сетевых запросов: URL, метод, тип, статус, размер, тела ответов для XHR/JSON;
  - `storage_state` (cookies/localStorage) для повторных заходов;
  - метаданные: финальный URL после редиректов, title, язык, время снятия, хэш DOM.
- **Обрезка DOM** (`dom_trimmer`): удаление скриптов, стилей, комментариев, SVG-путей,
  base64; сохранение landmark-структуры; ограничение до N токенов — это критично для
  локальной модели.
- Асинхронный запуск задач с прогрессом через WebSocket.
- Кэш снапшотов по хэшу URL+параметров, повторный заход без сети (офлайн-режим).

**DoD:** по 5 разным сайтам (SSR, SPA, каталог, новостной, с cookie-баннером) снапшот
снимается, сохраняется на диск и воспроизводится из кэша; размер обрезанного DOM
укладывается в лимит токенов.

---

### Этап 2. Анализ: карта элементов и ИИ-описания (8–12 дней)

**Цель:** получить машиночитаемую карту элементов страницы с описанием «за что отвечает».

- **Детерминированный предпроход** (до LLM, экономит токены и повышает точность):
  - кандидаты-интерактивные: `input`, `select`, `textarea`, `button`, `a`, `form`;
  - кандидаты-контейнеры повторов: алгоритм поиска списков — группы похожих
    sibling-узлов с совпадающей структурой (это и есть «карточки товаров», «строки таблицы»);
  - эвристики по атрибутам: `name`, `id`, `aria-label`, `placeholder`, `type`,
    `itemprop`, микроразметка Schema.org/OpenGraph;
  - определение готовых данных в сети: JSON-ответы API → предложить «парсить запрос,
    а не HTML» как приоритетный путь.
- **LLM-проход**: для каждой группы кандидатов — запрос со структурным выводом
  (JSON Schema) → `ElementMap`:
  ```json
  {
    "role": "search_input | product_card | price | pagination_next | ...",
    "description": "Поле поиска по каталогу",
    "selector": "form[role=search] input[name=q]",
    "selector_candidates": ["#search", "input.search-field"],
    "stability_score": 0.92,
    "sample_value": "ноутбук"
  }
  ```
- **Ранжирование селекторов**: скоринг по устойчивости — приоритет `data-*` и
  ARIA-атрибутам, штраф за автогенерированные классы (`css-1x2y3z`, хэши, длинные цифры).
  Храним **список** кандидатов, а не один селектор (основа self-healing на Этапе 6).
- **Генерация человекочитаемого отчёта**: «На странице 4 блока: шапка с поиском,
  фильтры, сетка из 24 карточек товара (название, цена, ссылка, картинка), пагинация».
- Промпты в отдельных файлах с версионированием; кэш ответов LLM по хэшу входа.

**DoD:** на тестовом наборе из 10 сайтов карта элементов корректно выделяет поиск,
карточки и пагинацию минимум в 8 случаях; отчёт читается человеком без пояснений;
полный анализ страницы укладывается в оговорённое время на локальной модели.

---

### Этап 3. Визуальный редактор элементов (7–10 дней)

**Цель:** пользователь видит карту и может её исправить, не зная CSS.

- Overlay-инспектор: страница отображается как iframe/screenshot со слоем подсветки;
  hover/click по элементу → выбор → присвоение роли и понятного имени.
- Панель карты элементов: список ролей с описанием, сэмплом значения, качеством селектора,
  возможностью переименовать роль («Наименование товара»), отключить лишнее,
  добавить своё поле.
- Ручное «дорисовывание»: режим выбора элемента кликом (Playwright picker или
  инъекция скрипта-инспектора), валидация селектора «находится ли он сейчас».
- Diff-подсветка: сколько узлов реально матчится (1 vs 24 — сразу видно, правильно ли
  определена карточка).
- Сохранение правок как **Scenario v1**.

**DoD:** пользователь без знаний CSS за 5 минут превращает авто-карту в корректный
сценарий на незнакомом сайте; все правки сохраняются и переприменяются.

---

### Этап 4. Движок извлечения (10–14 дней) — **ядро MVP**

**Цель:** сценарий даёт достоверные данные.

- **Резолвер селекторов**: выбор рабочего селектора из списка кандидатов в рантайме.
- **Стратегии извлечения** (по убыванию приоритета):
  1. `json_api` — повторный вызов найденного XHR-эндпоинта с параметрами (самый
     надёжный и быстрый путь для SPA);
  2. `dom_list` — обход контейнера-повтора, извлечение полей карточки;
  3. `dom_single` — одиночные поля страницы;
  4. `llm_fallback` — извлечение моделью по очищенному фрагменту HTML (дорого, редко).
- **Постобработка полей**: типы (`text`, `number`, `price`, `date`, `url`, `image`),
  транзакции: обрезка пробелов, нормализация цен (символы валют, разделители),
  преобразование относительных ссылок в абсолютные, парсинг дат, скачивание картинок,
  дедупликация записей по ключу.
- **Пагинация и глубина**: `next`-кнопка, `?page=N`, cursor/бесконечный скролл, лимит
  страниц, задержки между запросами (rate limit), возобновление после сбоя.
- **Раскрытие деталей**: переход на карточку для полного описания (двухуровневый сбор).
- **Валидация**: Pydantic-схема сценария, правила обязательности, отчёт о пропусках
  («на 3 из 100 записей нет цены»).
- **Ручной контроль**: предпросмотр первых N записей перед полным прогоном.

**DoD:** сценарий «собрать каталог с пагинацией» стабильно отрабатывает ≥3 страницы на
3 разных сайтах, даёт ≥95% заполненности ключевых полей, корректно нормализует цены и
ссылки, умеет продолжить прогон после падения.

---

### Этап 5. Хранение, результаты, экспорт (5–7 дней)

**Цель:** данные удобно смотреть, фильтровать и забирать наружу.

- Хранилище: SQLite — сущности `Site`, `Snapshot`, `ElementMap`, `Scenario`,
  `ScenarioVersion`, `Run`, `RunItem`, `Artifact`.
- Таблица результатов в UI: сортировка, фильтры, поиск, постраничный просмотр, экспорт
  выделенного; история запусков с diff «что изменилось с прошлого раза».
- Экспортёры: CSV (с выбором разделителя и кодировки), XLSX (типизированные колонки,
  автоширина), JSON/JSONL, Markdown, в буфер обмена; опционально Google Sheets.
- **Генератор ТЗ в Markdown** — второй выход ТЗ: по сценарию и карте элементов
  собирается документ «что и откуда брать, в каком формате, с какой логикой», пригодный
  для передачи внешнему ИИ-агенту или разработчику.
- Хранение артефактов (скриншоты, HTML, файлы) в `data/artifacts/<run_id>/` с очисткой
  по политике ретенции.

**DoD:** полный цикл от URL до XLSX-файла в руках пользователя, MD-ТЗ генерируется и
читается как готовое задание.

---

### Этап 6. Надёжность и self-healing (7–10 дней)

**Цель:** сценарии не ломаются от правок вёрстки и переживают сбои.

- **Валидация селекторов при запуске**: если упала заполненность полей — авто-пересборка
  карты элементов и предложение обновления с diff «было/стало».
- **Автопочинка**: перебор `selector_candidates` → LLM-ремап по новому снапшоту →
  пользователю предлагается патч сценария (никогда не применяем молча).
- **Ретраи и backoff** для сети, таймаутов, капчи; различение «сайт лёг» vs
  «селектор сломался».
- **Логи и наблюдаемость**: по каждому запуску — шаги, время, ошибки, скриншот при падении.
- **Антибот-гигиена**: реалистичный User-Agent, задержки, ограничение параллелизма на
  домен, уважение `robots.txt` (с явным переключателем ответственности пользователя).
- Опционально: расписание (APScheduler) и уведомления о завершении/изменениях (webhook,
  файл-отчёт).

**DoD:** искусственно сломанный селектор на тестовом сайте → система предлагает рабочую
замену; журнал запуска позволяет понять причину любого падения.

---

### Этап 7. Автоматизация ввода и сценарии-воркфлоу (10–14 дней)

**Цель:** закрыть вторую половину исходного ТЗ.

- **Действия**: `goto`, `fill`, `click`, `select`, `check`, `press`, `wait_for`,
  `upload_file`, `extract`, `loop`, `if`, `assert`, `screenshot`.
- **Параметризация**: значения из CSV/XLSX/формы UI — прогон сценария по списку строк
  («заполнить форму для 50 товаров»).
- **Запись сценария пользователем**: Playwright codegen-подобный режим — пользователь
  делает действия руками, UPA записывает и предлагает «очеловечить» их через ИИ.
- **Проверки**: assert на появление текста/элемента, сбор ошибок валидации формы.
- **Генерация кода**: экспорт сценария как самостоятельного Python-скрипта на Playwright
  (чтобы можно было запустить без UPA).
- **Ограничения-предохранители**: подтверждение перед отправкой форм/платежами,
  «сухой прогон» (dry-run) без фактической отправки, ограничение числа действий.

**DoD:** сценарий заполняет реальную форму на тестовом стенде для 20 строк входных данных
и отдаёт отчёт об успехах/ошибках по каждой строке.

### Этап 8. Упаковка, UX, документация (5–7 дней)

- Онбординг-визард, пустые состояния, понятные ошибки, тёмная тема.
- Установщик/лаунчер для Windows (например, PyInstaller + ярлык, либо Docker Desktop).
- Проверка наличия Ollama и модели, автозагрузка модели, понятный отказ без ИИ.
- Документация: быстрый старт, руководство по сценариям, FAQ по блокировкам, политика
  ретенции данных, дисклеймер об ответственности за соблюдение ToS сайтов.
- Шаблоны сценариев и примеры данных в комплекте.

## 4. Чем дополнить идею

### 4.1 Функциональные дополнения (высокая ценность)

1. **Парсить XHR/JSON, а не HTML.** Большинство современных сайтов сами получают данные
   JSON-запросом. Если UPA нашёл такой запрос в снапшоте — это самый стабильный и быстрый
   источник. Дать это как рекомендуемый путь по умолчанию.
2. **API-first режим (без браузера).** После разовой разведки браузером — повторные
   запуски через голый HTTP-клиент. Кратный выигрыш в скорости и ресурсах, меньший риск
   блокировки.
3. **Self-healing сценарии** (Этап 6) — главный дифференциатор. Без этого UPA = генератор
   одноразовых парсеров, которые ломаются через неделю.
4. **Мониторинг изменений как отдельный продукт.** «Следи за ценой/наличием/вакансией и
   сообщи, когда изменится» — самый частый реальный сценарий, требует минимум нового кода
   поверх Этапа 6.
5. **Библиотека шаблонов сценариев.** Маркетплейс/каталог заготовок: «каталог товаров»,
   «вакансии», «новости», «прайс-лист», «отзывы». Резко снижает порог входа.
6. **Двухуровневый сбор** (список → детальная карточка) с настраиваемыми полями детали —
   обязательная вещь для реальных каталогов.
7. **Инкрементальный сбор**: ключ дедупликации + «только новые записи с прошлого запуска».
8. **Экспорт прямо в приёмники**: Google Sheets, Airtable, PostgreSQL, S3, webhook — вместо
   «скачай CSV и разбирайся сам».
9. **Мультиязычность и мультирегион**: разные локали/валюты в одном сценарии, эмуляция
   геолокации.
10. **Авторизация**: сохранение сессии, поддержка логина по форме, ручной вход в headed-
    режиме с сохранением `storage_state`, работа с кабинетом за логином.
11. **Обратный режим: ввод данных из файла** (Этап 7) — «у меня 500 строк в Excel, заведи
    их в систему». Это второе большое направление ценности.

### 4.2 Технические дополнения (качество и надёжность)

12. **Кэш снапшотов и офлайн-повтор.** Разработка сценария не должна каждый раз ходить на
    сайт — быстрее, вежливее, воспроизводимо.
13. **Версионирование сценариев** с откатом, как в git. Изменения вёрстки → новая версия,
    а не потеря работы.
14. **Тестовый режим сценария (dry-run)** и «канареечный» запуск на 1 странице.
15. **Строгая схема данных сценария (Pydantic)** — гарантирует, что выход валиден, и
    позволяет сразу отдавать данные в код/БД без ручной чистки.
16. **Оценка стоимости и времени до запуска**: «~40 страниц, ~3 минуты, ~0 ₽ локально».
17. **Пул воркеров и ограничители**: не более N параллельных задач, лимит на домен,
    глобальный kill-switch.
18. **Изоляция выполнения**: запуск сценариев в отдельном процессе/контейнере, чтобы
    падение не роняло приложение; лимиты времени и памяти.
19. **Учёт юридической стороны в продукте**: явный чек-лист (robots.txt, ToS, персональные
    данные), лог согласия пользователя. Снижает риск и повышает доверие.
20. **Прокси-слой** (опционально) на случай блокировок, с явным предупреждением о
    соблюдении правил сайта.

### 4.3 Продуктовые дополнения

21. **Два режима работы в UI**: «Простой» (мастер из 3 шагов, всё автоматом) и
    «Продвинутый» (граф сценария, ручные селекторы, код). Один и тот же движок.
22. **Прозрачность ИИ**: показывать, почему модель решила, что это карточка товара
    (какие признаки), и уровень уверенности. Доверие к локальной модели без объяснений
    низкое.
23. **Работа без ИИ**: приложение должно оставаться полезным, если Ollama недоступна —
    ручной выбор элементов, детерминированные эвристики. ИИ — усилитель, не зависимость.
24. **Плагины/расширения для постобработки** (Python-функции на поле): «приведи к
    верхнему регистру», «вытащи артикул регуляркой».
25. **Диффы и аналитика**: график изменения цен, «новые позиции», «исчезнувшие позиции» —
    превращает парсер в аналитический инструмент.
26. **Локальность как фича**: подчеркнуть, что данные не покидают ПК; облачный ИИ —
    явный opt-in с предупреждением.

### 4.4 Что стоит уточнить в ТЗ (пробелы)

- **Масштаб**: десятки страниц или сотни тысяч записей? От этого зависит хранилище
  (SQLite → PostgreSQL) и архитектура воркеров.
- **Тип сайтов**: публичные каталоги, сайты за логином, внутренние корпоративные системы?
- **Расписание**: разовый сбор или регулярный мониторинг? Второе тянет за собой
  планировщик и уведомления.
- **Формат «ТЗ в MD»**: для какого именно ИИ-агента (Claude Code, Cursor, кастомный) — от
  этого зависит шаблон промпта и уровень детализации.
- **Что с капчей и антиботом**: UPA обходит (юридический риск) или честно сообщает
  «требуется ручное вмешательство»? Рекомендую второе.
- **Персональные данные**: собираем ли персональные данные и нужна ли маскировка/ретенция?
- **Многопользовательность**: строго один пользователь на локальной машине или несколько
  профилей с разграничением?
- **Лицензия и монетизация**: open-source, внутренний инструмент или продукт?

### 4.5 Риски

| Риск | Влияние | Митигация |
|---|---|---|
| Локальная модель слабо понимает вёрстку | Карта элементов мусорная | Обрезка DOM, структурный вывод, детерминированный предпроход, разрешить облачный фолбэк |
| Сайт блокирует автоматизацию | Сценарий не работает | API-first путь, задержки, реальный UA, headed-режим для ручного прохода |
| Вёрстка меняется | Сценарии умирают | Этап 6 (self-healing) + версионирование + мониторинг заполненности |
| Юридические претензии | Проект под угрозой | robots.txt/ToS-чек-лист, логи согласия, отказ от обхода капчи |
| Слишком широкое ТЗ («универсальный») | Никогда не готово | Жёсткий фокус MVP: каталоги товаров публичных сайтов; расширять после |
| Производительность Playwright на сотнях страниц | Долгие прогоны | Пул контекстов, API-first, кэш, батчинг |

## 5. Метрики успеха

- **Время до первых данных**: от вставки URL до первой таблицы — меньше 5 минут.
- **Конверсия авто-анализа**: доля сайтов, где карта элементов верна без правок ≥ 70%.
- **Стабильность сценария**: успешных перезапусков через 30 дней ≥ 90%.
- **Полнота данных**: заполненность обязательных полей ≥ 95%.
- **Автономность пользователя**: правки через UI без ручного написания CSS ≥ 80% случаев.
